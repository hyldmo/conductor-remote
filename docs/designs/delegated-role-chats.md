## Problem Statement

One Conductor chat runs one agent on one model. The user wants each phase of a task on the model suited to it: Fable plans, Spark explores, 5.6 Sol implements. Conductor offers per-chat model controls and a global default, no role table, and no way for one chat to open another with a chosen model. Fable is a Claude model, Spark and Sol are Codex models, and a Conductor chat runs one agent process, so a Codex explorer cannot be a subagent inside a Fable chat. It needs its own chat.

Same-provider routing is out of scope. User: "if i know im just gonna use the same provider i will just use subagents."

## What Makes This Cool

- **The planner grows its own workers.** Fable calls `delegate_task`, and a Spark tab appears beside it in the same workspace: configured, handoff attached, already running. Watchable from the phone.
- **The workspace reads as a pipeline.** Role chips on tabs and a plan / explore / implement strip with live status, because the relay keeps a registry of which chat holds which role. User: "If we save this config we can run custom ui for the tabs of agents tracked this way."
- **The result comes back on its own.** A baton (decision, evidence, files changed, risks, suggested next role) is sent into the planner's chat when the worker is done. Roo Code's orchestrator contract, applied to real cross-provider chats.
- **The eureka.** Orchestrators isolate one agent per worktree; routers pick a model per request. A role pipeline is one task done in sequence on one shared worktree, so the worktree is the handoff channel and the planner naming the role is the router. Nobody does this across providers.

## Constraints

- `conductor.db` is read-only. Every role fact lives in the relay's state dir.
- Every UI write runs behind `uiTurn`; agents get background priority. Tab open plus settings plus send is two or three UI turns of tens of seconds each. No HTTP request may be held past ~55s and the MCP client budget is 75s. So the tool answers fast and a queue does the work.
- Zero runtime dependencies. stdlib only.
- A role's model is a label from Conductor's own picker (the `list_models` cache), never free text. A missing model means re-pick. There is no fallback model.
- Spark has never run on this Mac (0 sessions) and is absent from the cached picker. One live picker refresh settles it before code. That drives the UI and needs a go-ahead.
- The relay restarts itself (autoupdate) and the Mac locks. The queue persists and parks exactly like the two existing ones.

## Premises (agreed)

1. Always a real Conductor chat. Crossing providers is the reason. The caller names the role. No subagent branch.
2. Assembled from actuators that exist: `openChat` (⌘T), `setModel` on the "Change agent" picker (provider follows the model; 86 workspaces here already mix Claude and Codex chats), the effort/plan/fast handlers, and the attachment token `split_chat` writes. No new AppleScript surface.
3. Model per role is a pick from the picker list. User: "theres no way to write a model freehand."
4. Roles are relay-owned config (`roles.json`) and relay-owned state (a session-to-role registry riding `/api/state`).
5. Revised after the Codex challenge: the result returns when the worker is idle, holds no open background task, and has written an assistant message after the delegated prompt's row. An `error` status returns as a failure. The notifier's one-more-tick survival rule applies.

## Recommended Approach: Delegation queue with a baton

### Data

- `stateDir()/roles.json`: `{ roles: { <name>: { model, effort?, plan?, fast?, preamble? } } }`. `model` is a picker label. Shipped defaults: `planning` = Fable, max, plan on; `exploration` = Spark, high; `implementation` = 5.6 Sol, xhigh (what new Codex chats here already use). A label is validated against `ModelCache` at save time and again at delegation time. A role whose model is gone answers `model_missing` with the current list, before any UI press.
- `stateDir()/delegations.json`: `{ id, parentSessionId, workspaceId, role, prompt, handoff: { throughRowid?, includeThinking }, status, childSessionId?, sentRowid?, attempts, reason?, createdAt, updatedAt }`. `status` is one of `queued | opening | configuring | sending | running | returning | returned | failed`. This file doubles as the role registry: `childSessionId → role`, plus the parent's own role (self-registered as `planning` on its first delegation unless the phone tagged it).

### Flow

1. `delegate_task({ role, prompt, session_id, workspace_id?, through?, include_thinking? })` validates the role and its model, writes a `queued` entry, and answers `{ delegation_id, role, model }` in about a second. Same body on `POST /api/sessions/:id/delegate`.
2. `DelegationQueue` (sibling of `FirstPromptQueue` and `ParkedPromptQueue`: same screen-lock gate, same background priority, same persisted file) advances one entry at a time per workspace:
   - `opening`: write the parent transcript cut as an attachment (`renderTranscript`, thinking on, tools off, `through` honoured), `openChat(ws)`, then find the new tab by diffing the tab list against the one read before ⌘T, as `split_chat` does.
   - `configuring`: `setAgentOptions(child, role)` and confirm `sessions.model` and the provider-specific effort column in the DB. Always press; a new tab's inherited agent type is unmeasured.
   - `sending`: `role.preamble` + `attachmentPrompt(token, prompt)` through `deliverPrompt`, so it inherits the retry loop, the transcript confirm, and `sendonce` keyed on the delegation id. Record the user row's rowid as `sentRowid`.
   - `running`: the watcher rides the notifier's poll. Child idle, `background_tasks` empty (`openBackgroundTasks`, gated on a live agent process), an assistant row with rowid above `sentRowid`, surviving one more tick. `status = error` moves on with a failure flag.
   - `returning`: write the child's transcript since `sentRowid` as an attachment, take the last assistant message as the baton (its `## Baton` section when present, the whole message otherwise), and `deliverPrompt` into the parent: "Delegated <role> task <id> finished." plus the baton plus the attachment token.
   - Failure policy as the first-prompt queue: three real attempts while unlocked, then `failed` and it stays, with a reason, dismissible by `DELETE`.
3. `/api/state`: each workspace carries `delegations: [{ id, role, status, parentSessionId, childSessionId, model, reason, updatedAt }]` at the same composition point as `pending_prompt`. The phone joins on session id.
4. Phone: a role chip on the tab after the title (the tab strip in `SessionView`), a pipeline strip above the transcript when a workspace has one or more delegations, the pending-bubble UI reused for an in-flight delegation in the parent and a "returning" bubble in the child. A roles editor in the settings sheet: per role, a model picker fed by the `useModels` cache, effort, plan, fast. Saves through `PATCH /api/roles`.
5. MCP: `delegate_task`, `list_roles`, `set_role`, `list_delegations`, `dismiss_delegation`. `list_chats` and `list_workspaces` print role and delegation status, for the same reason they print `pending_prompt` today.
6. Default preamble, every role: "You are the <role> agent for this workspace. End your final answer with a `## Baton` section: Decision, Evidence, Files changed, Risks, Suggested next role."

## Open Questions

- Is Spark in this Conductor's picker? One live `list_models` refresh answers it. If not, exploration's default is another Codex model until it is.
- Does a new tab inherit the parent's agent type or the global default? Unmeasured. The design always presses and confirms, so the answer only changes cost.
- The planner's turn should end after `delegate_task`, so the baton starts a fresh turn. If Fable keeps working and polls `read_chat`, the baton lands as steering into a running turn, which Conductor allows. The tool description says "delegate, then stop and wait."
- Several delegations from one parent return as separate prompts, FIFO per parent chat, like parked prompts. Whether the planner wants them batched is unknown until it runs.
- Cost per role (Roo issue 5376). `sessions.context_token_count` exists per chat and can feed a later per-role total. Not in this cut.

## Success Criteria

- From a Fable chat, one `delegate_task(role: "exploration")` produces a Spark tab in the same workspace within about a minute, model and effort confirmed in the DB, handoff attached, prompt sent, with each status visible on the phone on the way.
- The result returns into the Fable chat only after the Spark chat is idle with no open background task and a fresh assistant message. A backgrounded `sleep 30 &` in the worker does not trigger an early return.
- A relay restart mid-delegation resumes the entry. A locked Mac parks it. Three real failures show `failed` with a reason and a dismiss.
- A role naming a model the picker lacks is refused before any UI press, with the list offered.
- `tests/delegations.test.ts` drives the state machine tick by tick with fakes, as `tests/notify.test.ts` does. `tests/routes.test.ts` covers the new paths.
