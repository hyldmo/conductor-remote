## Problem Statement

One Conductor chat runs one agent on one model. The user wants each phase of a task on the model suited to it: Fable does planning work, Spark explores, 5.6 Sol implements. "Planning" is a delegated role, not Conductor's Plan mode: Plan mode is currently buggy and this feature must never enable or depend on it. Conductor offers per-chat model controls and a global default, no role table, and no way for one chat to open another with a chosen model. Fable is a Claude model, Spark and Sol are Codex models, and a Conductor chat runs one agent process, so a Codex explorer cannot be a subagent inside a Fable chat. It needs its own chat.

Same-provider routing is out of scope. User: "if i know im just gonna use the same provider i will just use subagents."

## What Makes This Cool

- **The planner grows its own workers.** Fable calls `delegate_task`, and a Spark tab appears beside it in the same workspace: configured, handoff attached, already running. Watchable from the phone.
- **One deliberate kickoff.** The Workflow pill in New workspace or an untouched `+` chat turns the first message into the configured planning root, disables ordinary agent settings, and records explicit permission to delegate. It does not turn on Conductor Plan mode.
- **The workspace reads as a pipeline.** Role chips on tabs and a plan / explore / implement strip with live status, because the relay keeps a registry of which chat holds which role. User: "If we save this config we can run custom ui for the tabs of agents tracked this way."
- **The result comes back on its own.** A baton (decision, evidence, files changed, risks, suggested next role) is sent into the planner's chat when the worker is done. Roo Code's orchestrator contract, applied to real cross-provider chats.
- **The eureka.** Orchestrators isolate one agent per worktree; routers pick a model per request. A role pipeline is one task done in sequence on one shared worktree, so the worktree is the handoff channel and the planner naming the role is the router. Nobody does this across providers.

## Constraints

- `conductor.db` is read-only. Global role definitions live in the relay's state dir; workspace-specific orchestration state lives under that worktree's ignored `.context/` directory.
- Every UI write runs behind `uiTurn`; agents get background priority. Tab open plus settings plus send is two or three UI turns of tens of seconds each. No HTTP request may be held past ~55s and the MCP client budget is 75s. So the tool answers fast and a queue does the work.
- Zero runtime dependencies. stdlib only.
- A role's model is a label from Conductor's own picker (the `list_models` cache), never free text. A missing model means re-pick. There is no fallback model.
- A fresh picker read now exposes two different Muse Spark labels. The shipped exploration template stays visibly invalid until the user chooses the exact one; the relay must not silently pick between them.
- Conductor Plan mode remains reachable through the relay's existing generic agent-settings API, but delegated roles do not store, expose, or apply it.
- The relay restarts itself (autoupdate) and the Mac locks. Active queue state must survive a relay restart while its workspace exists; archiving the workspace deliberately deletes that state with the worktree.

## Premises (agreed)

1. Always a real Conductor chat. Crossing providers is the reason. The caller names the role. No subagent branch.
2. Assembled from actuators that exist: `openChat` (⌘T), `setModel` on the "Change agent" picker (provider follows the model; 86 workspaces here already mix Claude and Codex chats), the effort/fast handlers, and the attachment token `split_chat` writes. The generic Plan handler remains unrelated to delegation. No new AppleScript surface.
3. Model per role is a pick from the picker list. User: "theres no way to write a model freehand."
4. Roles are relay-owned config (`roles.json`) and relay-owned state (a session-to-role registry riding `/api/state`).
5. Revised after the Codex challenge: the result returns when the worker is idle, holds no open background task, and has written an assistant message after the delegated prompt's row. An `error` status returns as a failure. The notifier's one-more-tick survival rule applies.

## Bounded UI findings (2026-09-03)

The configuration prerequisite is a GO. The full delegation loop is covered by injected fake-actuator tests; no delegated task prompt was submitted as part of this implementation pass:

- A provider-changing model selection rerenders the composer. Configuration must select the model alone, confirm the model plus `agent_type` in SQLite, reacquire the new provider's controls, apply only differing effort/fast values, and then confirm the complete requested state. A clean blank-chat repetition passed with exactly those two writes.
- Codex's measured effort ring is `none` (unnamed AX button) → `low` ("Light") → `medium` → `high` → `xhigh` ("Extra high") → `max` → `ultra` ("Ultra"). The relay keeps its existing wire key `ultracode` for the final value and translates at the actuator boundary.
- Plan mode is neither a role setting nor a completion signal. No live PoC or shipped delegated role may turn it on.
- `queue: true` returned the Baton as a distinct later turn. Nothing pending was visible in SQLite, and the eventual user row had `queue_order = NULL`, so the receipt is the eventual exact user row with a new turn—not queue metadata.
- Codex command sessions kept the child `working` and emitted no Claude `task_started` frames. The open-background-task guard remains extra protection for providers that emit those frames; it is not the primary completion signal.
- Live session statuses were only `idle`, `working`, and `error`. A worker question therefore returns as successful Baton content for the ordinary planning chat to interpret; v1 invents no paused/blocked status.

## Recommended Approach: Delegation queue with a baton

### Data

- `stateDir()/roles.json`: `{ version: 1, roles: { <name>: { model, effort?, fast?, preamble? } } }`. `model` is a required picker label, never free text. Shipped role templates name Fable, Spark, and 5.6 Sol, but each label is validated against the deduplicated `ModelCache` catalog at save time and again at delegation time. Cache groups are whole-menu snapshots named for the chat harness where they were observed, not provider ownership; provider identity is derived from the exact label. An unavailable label or unsupported provider family remains visibly invalid in Roles settings until the user picks a replacement; `delegate_task` refuses it before any UI operation. Plan mode is deliberately absent from this feature's schema.
- `<worktree>/.context/delegations/<id>.json`: one versioned active or failed job. The immutable envelope contains `parentSessionId`, `workspaceId`, `role`, the complete resolved role snapshot, `prompt`, `returnMode`, handoff options, current status, stage data, attempt counts, failure reason, and timestamps. A successful job is deleted after its baton lands. A failed job remains actionable until dismissed or until Conductor archives and deletes the workspace.
- `<worktree>/.context/delegations/sessions.json`: `{ version: 1, sessions: { <sessionId>: { role, delegationId?, assignedAt } } }`. This is identity for role chips, not job history. Parent self-registration and child assignments survive successful job deletion, then disappear naturally with the workspace.
- Version handling stays lean: accept only `version: 1`, validate every decoded field, expose a workspace-level state warning for malformed or unsupported files, and never erase one merely because it cannot be decoded. There is no migration framework; dismissal is the explicit delete path.
- Conductor remains the durable history: child chats, parent batons, and transcript attachments already preserve what happened. This feature does not keep a second orchestration log.

The role is resolved once, at intake:

```text
RoleStore                  immutable job envelope
planning ───────────────▶  role: planning
  model: Fable 5            resolvedRole:
  effort: max                 model: Fable 5
  fast: false                 effort: max
  preamble: ...               fast: false
                               preamble: ...
```

Editing `planning` later affects the next delegation, never a job already accepted.

### State machine

All status changes go through one local `transition()` function. It rejects illegal edges and verifies the fields required by the destination before persisting.

Keep the diagram below as an inline comment beside `transition()` in `src/delegations.ts`; recovery behavior is too easy to change accidentally when the legal edges are documented only outside the code.

```text
                              ┌──────── retry same stage ────────┐
                              │                                  │
queued ─▶ opening ─▶ configuring ─▶ sending ─▶ running ─▶ returning ─▶ returned
  │          │             │            │          │          │          │
  │          │             │            │          │          │          └─ delete job file
  │          │             │            │          │          │
  └──────────┴─────────────┴────────────┴──────────┴──────────┴────────▶ failed
                                                                        │
                                                                        └─ dismiss or archive

Required fields:
  queued        resolvedRole + parent/workspace/prompt/returnMode
  configuring   childSessionId
  sending       childSessionId + handoff attachment
  running       childSessionId + sentRowid
  returning     typed outcome + child completion row
  returned      parent delivery receipt
```

`opening`, `sending`, and `returning` are at-least-once across a relay restart. If the relay exits after the UI side effect lands but before the next file write, the stage can repeat. That narrow duplicate window is accepted; no reconciliation cursors or exactly-once protocol are added.

### Flow

0. The phone's **Workflow** pill in New workspace or an untouched `+` chat (plus `create_workspace { workflow: true }`) is the explicit workflow boundary. It requires an objective, rejects simultaneous model/effort/plan/fast settings, validates and freezes the `planning` role, and wraps the objective with delegation authority plus direct prohibitions on Conductor Plan mode and provider-native Agent/Task/subagents. The root must inspect `list_roles` and start tracked `delegate_task` sibling work instead of stopping at a plan. For workspace creation, `FirstPromptQueue` persists `sessionRole: planning`; once the session and worktree exist, it writes the root role assignment before applying model/effort/fast and delivering the prompt. For an existing pristine chat, the send route verifies idle + no prior user row and performs that same assignment/configuration order inside the idempotent send intent. Turning the pill off restores untouched ordinary agent choices.
1. `delegate_task({ role, prompt, session_id, workspace_id?, through?, include_thinking?, return_mode? })` and `POST /api/sessions/:id/delegate` call the same intake function. Intake resolves the parent workspace, rejects same-provider routing, validates the picker-backed role, freezes its full configuration and `returnMode`, atomically writes the `queued` job, wakes the queue, and answers `{ delegation_id, role, model }` without awaiting UI work. `return_mode` defaults to `queue`; `steer` is an explicit planner choice.
2. `DelegationQueue` is a single producer feeding the existing global `uiTurn` scheduler. It never fans out one AppleScript promise per workspace: Conductor has one window, so concurrent submissions add no throughput and can overflow `uiTurn`'s four waiting slots. Phone requests retain `uiTurn`'s existing interactive priority.
   - `opening`: render the requested parent transcript cut with thinking on and tools off, write it through the existing attachment helper, open a real sibling chat, and identify it by diffing session ids from before and after ⌘T.
   - `configuring`: apply the frozen role in two stages. First select the model alone and confirm its id/label plus `agent_type` in SQLite. Then reacquire the rerendered composer, apply only effort/fast values that differ from SQLite, and confirm the complete role snapshot. The inherited defaults of a new tab are irrelevant. Delegation never changes or relies on Plan mode; if a child has inherited it, configuration fails before the task is sent.
   - `sending`: combine the role preamble, attachment token, and task prompt; call the existing delivery loop using the delegation id as the in-process deduplication key; then persist the matching user row as `sentRowid`.
   - `running`: observe the child on the shared session poll. Base session state comes from the existing global query; assistant cursors and background-task frames are read only for active child session ids. Poll listeners never await AppleScript or push network work.
   - `returning`: render only the child's rows after `sentRowid`, parse the final assistant message's `## Baton` section when present and otherwise use the whole message, write the transcript attachment, then send the typed outcome to the parent. `queue` asks Conductor to start a new turn when the parent is working; `steer` deliberately injects into its current turn.
   - `returned`: persist the transition only long enough to see the eventual exact user row in the parent on a new turn, then delete the job file. A queued return has no pending SQLite row and its dispatched row has `queue_order = NULL`, so neither is a receipt. The session-role registry remains.
   - `failed`: after three real unlocked failures, keep the file and reason visible. Lock-blocked attempts and a saturated UI queue cost nothing. Dismissal removes only the failed job, never the role map or either chat.
3. `SessionPoller` owns one two-second clock and one base `Reads.listSessionStates()` call. The notification watcher and delegation queue subscribe synchronously. Notification settings gate only the final push; they never stop the poller or delegation progress. A transient read error is logged and the next tick continues.
4. Completion is typed and stable for two ticks:
   - `success`: child is `idle`, has no open background task, and has a fresh assistant row after `sentRowid`.
   - `error`: the error status survives the second tick; return an error outcome even when no fresh assistant prose exists.
   A question or request for approval is ordinary assistant content inside a successful Baton. The planning chat decides what to do next; v1 has no paused or blocked outcome because Conductor exposes no such session status.
5. `/api/state` attaches only active and failed jobs plus the worktree's session-role map to each live workspace. Build a `workspaceId → delegation projection` map once per request rather than filtering the whole queue for every workspace.
6. Phone: add role chips to chat tabs, an active pipeline strip above the transcript, and parent/child queue bubbles. Extract a presentational `QueueBubble`; pending prompts and delegations retain separate wire types and their own actions. The Roles section uses the existing model picker and exposes model, effort, and fast controls. New workspace and an untouched `+` chat put a Workflow pill directly after the model picker; active mode displays the planning role read-only, hides Plan, requires an objective, and makes the first send start the workflow. The pill disappears after a user row, pending workflow kickoff, or role assignment. An unavailable selected model is shown as invalid instead of silently replaced.
7. MCP: add `delegate_task`, `list_roles`, `set_role`, `list_delegations`, and `dismiss_delegation`. Delegation lists contain active and failed work only. `list_chats` and `list_workspaces` print role and active delegation state.
8. Default preamble, every role: "You are the <role> agent for this workspace. End your final answer with a `## Baton` section: Decision, Evidence, Files changed, Risks, Suggested next role."

Keep a compact poll-fanout ASCII comment in `src/session-poller.ts` showing that the clock and base read are shared while notification delivery and delegation detail reads are downstream listeners. That ownership boundary is the protection against accidentally gating orchestration on push settings again.

## Success Criteria

- After the user selects a valid picker-backed exploration model, one `delegate_task(role: "exploration")` from an ordinary Fable chat produces that configured tab in the same workspace within about a minute, with model and effort confirmed in the DB, handoff attached, prompt sent, and each status visible on the phone on the way. Neither role activates Plan mode.
- Enabling Workflow while creating a workspace or sending the first message in a pristine `+` chat resolves the configured planning role, sends no explicit Plan setting, tags the session as `planning` before delivery, and gives the root explicit authority to use the same `delegate_task` path. Invalid planning configuration prevents creation/delivery; switching Workflow off leaves ordinary staged settings intact.
- The result returns into the Fable chat only after the configured exploration chat is idle with no open background task and a fresh assistant message. A backgrounded `sleep 30 &` in the worker does not trigger an early return.
- A relay restart scans live worktrees and resumes active job files. The accepted at-least-once window is documented and tested. A locked Mac parks progress without spending attempts. Three real failures show `failed` with a reason and a dismiss.
- A role naming a model the picker lacks is refused before any UI press, with the list offered.
- A returned job file is removed, both Conductor chats remain, and their role chips survive from the worktree's session-role map until the workspace is archived.
- Focused Vitest suites drive every transition, persisted state, poll gate, HTTP/MCP path, and phone state; one fake-actuator integration test covers intake through returned baton.

## Production Failure Modes

| Codepath | Real failure | Test | Handling | User-visible result |
|---|---|---|---|---|
| Role save/intake | Cached picker label disappeared | Yes | Reject before UI | Invalid role names the missing model and offers the current list |
| Job decode | Partial or unsupported JSON | Yes | Preserve the file and emit a workspace state warning | Unreadable state is visible and can be dismissed rather than silently reset |
| Startup recovery | Worktree was archived | Yes | Drop the in-memory job; Conductor already deleted its workspace | Workspace and orchestration disappear together |
| Opening | Another tab appears during ⌘T | Yes | Require one unique id diff; retry then fail | Failed bubble names ambiguous tab creation |
| Configuring | Model, effort, fast, or provider does not stick | Yes | Staged DB confirmation fails; retry budget applies | Failed bubble names configuration failure |
| Sending | UI reports failure after prompt actually landed | Yes | Existing transcript receipt detects it | Job proceeds without a same-process duplicate |
| Restart during UI side effect | File still names the prior stage | Yes | Retry at least once | A duplicate tab, child prompt, or baton is possible and documented |
| Completion | Child reads idle while background task runs | Yes | Targeted task read blocks completion | Pipeline remains running/waiting |
| Completion | Status flickers idle for one poll | Yes | Require a second stable tick | No early baton |
| Worker question | Agent requests approval or input in its answer | Yes | Return it as successful Baton content | Planning chat receives the question and chooses the next action |
| Returning | Parent is working | Yes | `queue` starts the next turn; `steer` injects intentionally | Behavior matches the planner's frozen choice |

| Step | Modules touched | Depends on |
|---|---|---|

```text
Phase 1: Contract and codecs (sequential foundation)
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
Lane A: relay   Lane B: MCP  Lane C: phone     (parallel)
          └─────────┼─────────┘
                    ▼

```

The three parallel lanes touch separate primary modules after the contract lands. Keep `routes.ts` and `wire.ts` in the foundation lane; otherwise all three branches will conflict there.

## NOT in scope

- Same-provider delegation: use native subagents when the provider already matches.
  A separate one-way continuation for context-heavy tasks is captured in
  [`context-rollover.md`](./context-rollover.md); it does not weaken this feature's
  cross-provider contract.
- Filesystem intake/watchers: `.context/delegations/<id>.json` is relay-written state in this cut, not a plain-Write API for agents without MCP.
- Exactly-once recovery across relay restarts: accepted as disproportionate code for a narrow duplicate window.
- Bidirectional question relaying: a worker can return a question in its Baton, but v1 does not keep it open while relaying a second conversation.
- Historical orchestration graphs or logs: Conductor chat history is sufficient until real usage proves otherwise.
- Per-role token or cost totals: the data exists per session but does not affect routing correctness.
- Conductor Cloud support: this repository remains intentionally local-macOS-only.
- New AppleScript handlers or a second UI scheduler: existing actuators and `uiTurn` are sufficient.
