## Problem Statement

The user runs ~46 live Conductor workspaces (measured: 2 working, 14 touched in the last 24h with 4 unread chats, 6 idle 1–7d, 24 idle >7d; labels: 16 in-review, 15 in-progress, 9 backlog). In-progress work stalls because answering agents needs a screen and typing, and commute/walking time is exactly when neither is available. Mental bandwidth is the second constraint: nobody can absorb 10 pages of plan docs by ear. The user's own serialization insight frames the product: "we don't have to multitask several chats at once. We can do one at a time and once that one's agents are working, switch to another."

## North Star

Codex's cold-read, adopted verbatim as the target feel: **"a commute control room with an interruption budget. Agents don't just wait in a list; the relay turns their state into a serial radio queue. Each item is: situation, decision needed, safe options, consequence, then a read-back and dispatch. The user works one thread to a stable handoff, says 'next,' and the system remembers where the call left off. At the end: 'Three decisions made; five agents unblocked; two need a screen later.' It feels less like voice chat and more like operating a small engineering organization from a walk."**

## What Makes This Cool

Dial a number from a locked phone in a pocket. Hear "two working, five need you, thirty dormant." Unblock five agents with five spoken decisions. Arrive at the office with warm worktrees. The heavy thinking never moves: workspace agents already write turn-final summaries (Conductor instructs them to), so the fleet itself is the summarization midlayer, and the voice layer stays deliberately dumb.

## Constraints

- Phone is locked, in a pocket: only a call-shaped audio session survives (kills PWA WebRTC for v1; it stays a foreground mode later).
- No native app of our own (App Store treadmill; React Native is a possible phase 3 that would collapse softphone + visuals into one surface).
- Free OSS inside conductor-remote: zero runtime deps in the relay, no LLM in the relay, user brings their own OpenAI key.
- Voice-capped reads enforced in relay code, not prompt discipline: caps are what prevent context/cost explosion and cognitive overload at once.
- User is in Oslo: no international-call cost in any variant (direct SIP bypasses PSTN; optional local number makes it a domestic call).
- Wrong-target writes are the worst failure (same as the repo's existing send philosophy): every dispatch is read back and structurally confirmed.

## Premises (all agreed)

- **P1** Native app voice modes can't host this today (verified: ChatGPT voice has no MCP; Claude voice supports only first-party integrations). Future Claude-voice custom connectors = free upgrade; recheck quarterly.
- **P2** Buy the voice layer only: `gpt-realtime` accepts a remote MCP URL in session config and handles tool calls; start on `gpt-realtime-mini` (~$0.02–0.05/min cached; flagship ~$0.06–0.11/min). Named fallback if the brain is too weak: compose LiveKit/Pipecat + Claude brain. Cost at daily commute use: roughly $9–50/month, dominated by model audio, transport is noise.
- **P3** Transport is a SIP call into OpenAI's EU endpoint (`sip:<project>@sip.api.openai.com`, TLS). **Revised after the live probe (2026-09-01):** direct SIP works, verified from a real UA (baresip on the Mac: 180 Ringing in 0.5s, webhook, accept, call answered) — but the softphone-as-phone-client path is demoted, because project ids are case-sensitive in the SIP user part and Linphone lowercases them (rings 15s → 400 Bad Request; known bug family, linphone-iphone #296; no bypass found on iOS). Primary phone client is therefore the **Twilio number** (trunk or TwiML `<Dial><Sip>`, case pinned in config; ~$2–6/mo, zero mobile data, native dialer; Norwegian number needs the regulatory bundle). Audio: all telephony is G.711 narrowband; WebRTC is the wideband path, foreground-only. Data use: ~25–30 MB per 20-min SIP call, ~6–10 MB on WebRTC.
- **P4** The durable build is deterministic, voice-capped briefing reads in the relay, tested offline against real chat history. No LLM in the relay, in any version.
- **P5** Free OSS feature; per-call cost logged and documented from measurement, not estimates.
- **P6** The voice model routes, never thinks: capped briefs for breadth; depth is forwarded to the workspace agent that owns the context (`send_prompt` → its final message is the answer); read-back before every send. Working agents are a special case: forwarding into a running turn is steering, so the orchestrator says so and asks before touching one.

## Recommended Approach: B — the standup product

Everything rides the existing relay: `/mcp` transport, token gate (Bearer or `?token=`), `send_prompt` with its retry/parked/confirm machinery, `notify.ts` turn-end detection, push pipeline with `chatRoute` deep links, read marks in prefs, `set_workspace_status`.

New pieces:

1. **Voice-capped briefing tools** (the durable core). `voice_roll_call()` → "N working, M need you, K dormant" plus the queue heads. `voice_next_decision(cursor)` → one item in the north-star grammar: situation, decision needed, safe options, consequence. Hard caps on every spoken field. Ranking, computed live from DB signals each call: error > idle-with-question (parsed from the last message, AskUserQuestion options included) > unread finished turns (read marks) > recent activity; workspaces idle >7d or labelled backlog/done are dormant — counted, never spoken unless asked.
2. **Session broker** in the relay: the OpenAI SIP webhook endpoint. Screens callers, accepts, attaches the narrow system prompt + MCP URL + voice. Holds the session WebSocket for nudges.
3. **`voice_send_preview` → confirm token → send.** The model cannot reach `send_prompt` without first creating a preview naming target chat and exact text, and hearing "yes, send." Read-back enforced structurally, matching the repo's fail-closed ethos.
4. **Call cursor, dropped-call semantics only** (user-pinned): survives a redial within ~10 min ("picking up where we left off"); past TTL, fresh roll-call. The queue itself is never stored — recomputed live, so desk work at the Mac self-heals it (answered questions and cleared unreads simply stop appearing). Only the cursor marks what this call already handled.
5. **Forward-to-owner deep dives with mid-call nudges.** "Ask berlin why CI failed" → `send_prompt`; the call moves on; when `notify.ts` sees the turn end, the broker injects a conversation item and the orchestrator speaks the answer. Idle chats only by default; working chats get the steering warning.
6. **Artifact hand-off to the lock screen.** A relay hook the voice agent calls: fires the existing push pipeline with the existing chat deep link ("screenshot's on your lock screen"). Phase-2 follow-the-call (PWA tracks an orchestrator cursor) deferred.
7. **Voice grooming.** "Push zigbee to backlog" → `set_workspace_status`. "Snooze the lamp thing until Thursday" → relay-side snooze store (own state file, never Conductor's DB), which also holds the end-of-call "needs a screen later" list, surfaced in the PWA.
8. **End-of-call tally**: "Three decisions made, five agents unblocked, two need a screen later."
9. **Per-call cost log**: call id, tool calls, latency, token counts, estimated cost, in the relay log.

## Open Questions

- Is `gpt-realtime-mini` a good enough presenter, or does brief delivery need the flagship? (Escape hatches ordered: flagship → Pipecat+Claude brain.)
- ~~Does direct SIP dialing to `sip.api.openai.com` work?~~ **Resolved 2026-09-01, the assignment ran:** yes over TLS from a real UA; the webhook event is `realtime.call.incoming` exactly as documented; a lowercased project id rings ~15s then 400s with no webhook. Webhook delivery verified via a plain-443 tunnel; delivery to a nonstandard `:8443` Funnel port remains untested.
- Caller screening strength: SIP `From` is spoofable; worst case is someone burning API credits until rejected. Investigate a secret in the dialed URI / early-media PIN if it matters. (Moot on the Twilio path: only the number routes to the trunk.)
- Nudge injection mechanics: confirm the broker can attach to a SIP-originated session over WebSocket and inject items mid-call.
- When Claude voice mode opens custom connectors, what carries over? (Everything except the broker, by design.)

## Success Criteria

- Acceptance demo (Codex's, adopted): call in, hear a roll-call that matches the DB, resolve one real agent question, hear the exact prompt read back, say yes, verify one user row in the right chat, hear the next decision.
- Fixture tests over real local chat history assert every spoken field fits its speech budget, and the ranking pins error/question/unread/recency order.
- Cost: a logged real commute call lands within the estimated band; the README documents the measured number.
- Habit: used on real commutes five days in a row without reaching for the screen (except lock-screen artifacts).
