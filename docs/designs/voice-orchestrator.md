## Problem Statement

The user runs ~46 live Conductor workspaces (measured: 2 working, 14 touched in the last 24h with 4 unread chats, 6 idle 1–7d, 24 idle >7d; labels: 16 in-review, 15 in-progress, 9 backlog). In-progress work stalls because answering agents needs a screen and typing, and commute/walking time is exactly when neither is available. Mental bandwidth is the second constraint: nobody can absorb 10 pages of plan docs by ear. The user's own serialization insight frames the product: "we don't have to multitask several chats at once. We can do one at a time and once that one's agents are working, switch to another."

## North Star

Codex's cold-read, adopted verbatim as the target feel: **"a commute control room with an interruption budget. Agents don't just wait in a list; the relay turns their state into a serial radio queue. Each item is: situation, decision needed, safe options, consequence, then a read-back and dispatch. The user works one thread to a stable handoff, says 'next,' and the system remembers where the call left off. At the end: 'Three decisions made; five agents unblocked; two need a screen later.' It feels less like voice chat and more like operating a small engineering organization from a walk."**

## What Makes This Cool

Dial a number from a locked phone in a pocket. Hear "two working, five need you, thirty dormant." Unblock five agents with five spoken decisions. Arrive at the office with warm worktrees. The heavy thinking never moves: workspace agents already write turn-final summaries (Conductor instructs them to), so the fleet itself is the summarization midlayer, and the voice layer stays deliberately dumb.

## Constraints

- Phone is locked, in a pocket: only a call-shaped audio session survives (kills PWA WebRTC for v1; it stays a foreground mode later).
- No native app of our own (App Store treadmill; React Native is a possible phase 3 that would collapse softphone + visuals into one surface).
- Free OSS inside conductor-remote: zero runtime deps in the relay, no LLM in the relay, user brings their own OpenAI key. The broker's outbound socket is Node 24's global `WebSocket` client, so the zero-deps rule holds.
- Voice-capped reads enforced in relay code, not prompt discipline: caps are what prevent context/cost explosion and cognitive overload at once.
- User is in Oslo: no international-call cost in any variant (direct SIP bypasses PSTN; optional local number makes it a domestic call).
- Wrong-target writes are the worst failure (same as the repo's existing send philosophy): every dispatch is read back and structurally confirmed.
- **Public ingress is required for exactly two URLs OpenAI's servers must reach**: the call webhook and the voice MCP endpoint (OpenAI's docs: "The Realtime API calls the remote MCP server"). Everything else stays on the tailnet. The relay itself has run tailnet-only since PR #54 and keeps doing so (D2: a dedicated voice listener on Funnel `:8443`).
- **The Mac must be unlocked and awake for a dispatch to land.** A locked Mac parks every send (`src/parked.ts`, the `lockBlocked → park` branch of the send route). `keep_awake` plus `PREVENT_SCREEN_LOCK` is what makes an unattended Mac dispatchable; the roll call states the lock state first, and the tally counts parked sends apart from landed ones.
- **The phone number and the SIP URI are credentials.** A caller is gated before OpenAI is bridged; a session that reaches the voice tools can dispatch prompts, so "someone burning API credits" was never the worst case. The gate keeps strangers out; it does not, and cannot, limit what an authenticated caller asks for.
- **The relay token never leaves the Mac.** The voice session gets its own endpoint and its own scoped token (D4). That bounds what the credential can do when it is not the user holding it (it sits in OpenAI's session store), and what the model can do when a chat's last message tells it to: no direct send exists on that endpoint, so a read-back is the only way a prompt leaves.

## Premises (all agreed)

- **P1** Native app voice modes can't host this today (verified: ChatGPT voice has no MCP; Claude voice supports only first-party integrations). Future Claude-voice custom connectors = free upgrade; recheck on 2026-12-01 (issue #190).
- **P2** Buy the voice layer only: `gpt-realtime` accepts a remote MCP URL in session config and handles tool calls; start on `gpt-realtime-mini` (~$0.02–0.05/min cached; flagship ~$0.06–0.11/min). Named fallback if the brain is too weak: compose LiveKit/Pipecat + Claude brain. Cost at daily commute use: roughly $9–50/month, dominated by model audio, transport is noise.
- **P3** Transport is a SIP call into OpenAI's EU endpoint (`sip:<project>@sip.api.openai.com`, TLS). **Revised after the live probe (2026-09-01):** direct SIP works, verified from a real UA (baresip on the Mac: 180 Ringing in 0.5s, webhook, accept, call answered) — but the softphone-as-phone-client path is demoted, because project ids are case-sensitive in the SIP user part and Linphone lowercases them (rings 15s → 400 Bad Request; known bug family, linphone-iphone #296; no bypass found on iOS; upstream report tracked in issue #189). Primary phone client is therefore the **Twilio number** (TwiML `<Dial><Sip>`, case pinned in config; ~$2–6/mo, zero mobile data, native dialer; Norwegian number needs the regulatory bundle). Audio: all telephony is G.711 narrowband; WebRTC is the wideband path, foreground-only. Data use: ~25–30 MB per 20-min SIP call, ~6–10 MB on WebRTC. **Eng review correction:** the number does not authenticate the caller; anyone who dials it reaches the session. The gate in piece 3 below is what does.
- **P4** The durable build is deterministic, voice-capped briefing reads in the relay, tested offline against real chat history. No LLM in the relay, in any version.
- **P5** Free OSS feature; per-call cost logged and documented from measurement, not estimates.
- **P6** The voice model routes, never thinks: capped briefs for breadth; depth is forwarded to the workspace agent that owns the context (`send_prompt` → its final message is the answer); read-back before every send. Working agents are a special case: forwarding into a running turn is steering, so the orchestrator says so and asks before touching one.

## Cross-Model Perspective

Codex (gpt-5.6-terra, cold read, no premise challenged; independently converged on direct SIP + remote MCP over Pipecat-in-v1): coolest version is the control room above; the revealing user line is "dumb agent could just read that summary" — the product is a switchboard, and its restraint is the feature; Pipecat is the 50% escape hatch, and the valuable 50% is conductor-remote-specific (briefing tools, decision queue, read-back semantics, forward-to-owner loop, cost records, offline replay tests). Weekend build: `voice_roll_call` + `voice_next_decision` + preview-gated send + fixture tests + cost log. Adopted from Codex: the resumable call cursor, the end-of-call tally, and `voice_send_preview` as a structural gate.

Codex again, as the eng review's outside voice (2026-09-02, cold read of this doc against the repo): the preview gate is decoration while `/mcp` exposes `send_prompt` beside it; the shared token is full remote control of the Mac and must not reach a vendor session; the Twilio number authenticates nothing; a locked Mac parks every dispatch; the WebSocket control channel is unverified and load-bearing; voice retries are not idempotent without a persisted one-use record; the question grammar is the fragile piece; read marks need a voice-side writer. All of these are folded in below. Two points were weighed and not adopted: "the relay has no WebSocket implementation" (the broker needs an outbound client, which Node ships), and "validate one-item briefing by phone before SIP or Twilio" (there is no "by phone" without them).

## Approaches Considered

- **A: Weekend dial-in** (minimal viable) — Codex's prototype: two capped briefing tools, preview-gated send, webhook broker, softphone SIP, fixture tests, cost log. Not chosen as the end state; survives intact as the first commit group.
- **B: Standup product** — CHOSEN, see below.

## Recommended Approach: B — the standup product

Everything rides the existing relay: the MCP tool machinery (`createTools`'s `Tool` interface and injected `call`), `send_prompt` with its retry/parked/confirm machinery and the `sendOnce` memo, `notify.ts`'s `chatRoute` and `notifyAll`, read marks in `prefs.json`, `set_workspace_status`, the token-file pattern for secrets, and `dev-server.ts`'s second-port `tailscale serve` pattern with an ownership receipt.

New pieces, as revised by the eng review:

1. **Voice-capped briefing tools** (the durable core, `src/voice/brief.ts`). `voice_roll_call()` → lock state first ("Mac is unlocked" / "Mac is locked, sends will park"), then "N working, M need you, K dormant" plus the queue heads. `voice_next_decision(cursor)` → one item in the north-star grammar: situation, decision needed, safe options, consequence. Every spoken field goes through `clipExact` (marker inside the cap), roll call ≤ ~600 chars, decision ≤ ~400. Ranking, computed live from DB signals on every call: `error` > `needs_user_input` / `needs_plan_response` > idle with a question in its last message > unread finished turns > recent activity; dormant = idle >7d or `manual_status`/`derived_status` in backlog/done/canceled, counted, never spoken unless asked. **The real signals, measured 2026-09-02:** `needs_plan_response` and `needs_user_input` are **transient** (issue #102: they exist only while the wait is open and collapse back to `idle` once answered), so a survey of stored values shows only `idle`/`working`/`error` and looks complete when it is not; when one is present it is the strongest "needs you" signal there is. `turn_started_at` is null on every live chat (`queue_order` last written 2026-08-31 10:14), so recency keys on `sessions.updated_at` and the last user row. And in this setup a question is usually **prose**, because `AskUserQuestion` is disabled under Conductor and gstack renders a decision brief instead (`D<N> —` title, lettered options, `Recommendation:` line, `(recommended)`). The parser reads that grammar out of `lastAssistantText`, falls back to a structured `AskUserQuestion` input when one is present, and degrades to "last paragraph, clipped" when neither parses. When the call handles an item (dispatched, or skipped aloud), the relay writes a read mark for it, so the cursor and the marks converge instead of fighting.
2. **Voice listener and endpoint** (`src/voice/server.ts`, D2 and D4). A second loopback port serving only `/voice/webhook`, `/voice/twiml` and `/voice/mcp`, fronted by Funnel on 8443 (10000 as fallback; Funnel allows 443, 8443, 10000 only) with an ownership receipt like `dev-forwards.json`, so `yarn deploy` never clobbers it and the main relay stays tailnet-only. `/voice/mcp` serves `createVoiceTools(call)` and nothing else, behind its own 0600 token; its loopback calls carry `x-relay-client: voice`, which maps to `interactive` priority, because the person on the phone is the human. `allowed_tools` in the session config is belt and braces on top. Finding the routes gives an attacker nothing: each is behind a secret (voice token, OpenAI signing secret, Twilio auth token) and nothing here ever dials out.
3. **Caller gate, before OpenAI is bridged** (`src/voice/twiml.ts`, `src/voice/webhook.ts`). The TwiML endpoint verifies `X-Twilio-Signature`, allowlists `From`, and `<Gather>`s a DTMF PIN; only then does it return `<Dial><Sip>` with the case-pinned OpenAI URI carrying a trunk marker header (an HMAC over call id and time). The OpenAI webhook verifies the Standard Webhooks signature (`webhook-id`, `webhook-timestamp`, `webhook-signature`, five-minute tolerance, replay of `webhook-id` refused) and the marker, and answers `/reject` (603) for anything else, so a direct dial of the SIP address with a known project id creates no session and spends nothing. **The marker depends on OpenAI passing custom SIP headers through to `sip_headers`, which the docs do not state** (they list From, To, Call-ID); probe 0 settles it. If they do not pass, the fallback is layered rather than structural: match the caller id Twilio sets on the bridged leg, and treat the project id as a secret rotated by creating a new OpenAI project. On the direct-SIP path the marker is the only gate, so that path stays documented as "your own softphone, your own risk".
4. **Session broker** (`src/voice/broker.ts`). Accepts with the narrow system prompt, voice, and `tools: [{type:'mcp', server_url: <voice mcp>, headers: {authorization: Bearer <voice token>}, require_approval: 'never'}]`, then opens the outbound `wss://api.openai.com/v1/realtime?call_id=…` socket (Node global `WebSocket`). The socket is where `response.done.usage` arrives for the cost log, where `mcp_call` events give per-tool latency, and where the broker injects items (`conversation.item.create` + `response.create`). Active call ids persist to `stateDir()/voice-calls.json` so a self-update restart re-attaches on boot.
5. **`voice_send_preview` → one-use record → async `voice_send`** (D3). The preview names the target chat and the exact text and returns a token; the record is persisted, one-use, with a two-minute TTL. `voice_send(token)` re-checks the chat is still idle (a `working` chat is a spoken steering refusal), then returns `queued` in under a second and runs `deliverPrompt` with the token as `sendOnce`'s `clientId`, so a model retry or a redial cannot type the prompt twice. **The call assumes a queued send lands** (user-pinned): a landed send stays silent and the conversation moves on; the broker injects a line only when it did not land, "parked until the Mac unlocks" or the failure text. Expired, foreign-session and text-mismatch tokens each have their own spoken sentence, pinned by test.
6. **Call cursor, dropped-call semantics only** (user-pinned): survives a redial within ~10 min ("picking up where we left off"); past TTL, fresh roll-call. The queue itself is never stored — recomputed live, so desk work at the Mac self-heals it (answered questions and cleared unreads simply stop appearing). Only the cursor marks what this call already handled.
7. **Forward-to-owner deep dives with mid-call nudges.** "Ask berlin why CI failed" → `send_prompt`; the call moves on; the broker keeps a per-call watch list (session id plus the rowid at forward time) and polls `lastAssistantText` on its own 2s timer only while a call is live, then injects the answer. It does not ride `notify.ts`'s tick, which resets itself whenever no push device is subscribed and carries push-only rules. Idle chats only by default; working chats get the steering warning.
8. **Artifact hand-off to the lock screen.** A relay hook the voice agent calls: fires the existing push pipeline (`notifyAll`) with the existing chat deep link (`chatRoute`), "screenshot's on your lock screen". Phase-2 follow-the-call (PWA tracks an orchestrator cursor) deferred.
9. **Voice grooming.** "Push zigbee to backlog" → `set_workspace_status`. "Snooze the lamp thing until Thursday" → relay-side snooze store (own state file, never Conductor's DB), which also holds the end-of-call "needs a screen later" list, surfaced in the PWA.
10. **End-of-call tally**: "Three decisions made, four agents unblocked, one parked until the Mac unlocks, two need a screen later."
11. **Per-call cost log**: call id, tool calls with latency, token counts from `response.done.usage`, estimated cost, in the relay log.
12. **Secrets and config.** OpenAI key, webhook secret, Twilio auth token, caller allowlist and PIN live in `stateDir()/voice.json` (0600), following the token file, never `settings.json` (it is served by `/api/settings`) and never the LaunchAgent plist (user-readable; `scripts/service.ts` keeps the token out of it on purpose). `redactSecrets` learns `sk-` and `whsec_` so `relay_logs` cannot echo either. Speech bounding helpers (`oneLine`, `clipExact`) move to one `src/speech.ts` shared with `notify.ts`.

### Call flow

```
phone ──PSTN──▶ Twilio ──POST /voice/twiml──▶ relay: voice listener (Funnel :8443)
                  │  X-Twilio-Signature ✓, From allowlisted ✓, <Gather> PIN ✓
                  ◀── <Dial><Sip>sip:proj_…@sip.api.openai.com;transport=tls?X-Relay-Call=hmac
                  │
              OpenAI SIP ──realtime.call.incoming──▶ POST /voice/webhook
                  │            signature ✓, marker ✓ → POST /v1/realtime/calls/:id/accept
                  │            {instructions, voice, tools:[{type:mcp, server_url:/voice/mcp,
                  │             headers:{authorization: Bearer <voice token>},
                  │             require_approval:'never'}]}
                  │
                  ├──tools/list, tools/call──▶ /voice/mcp → createVoiceTools(call)
                  │                              roll_call · next_decision · send_preview
                  │                              send (async, answers "queued")
                  │                              forward · artifact · status · snooze
                  │
                  ◀──wss://api.openai.com/v1/realtime?call_id=… (outbound client)──┐
                        broker: response.done.usage → cost line                    │
                                parked/failed send, forwarded answer → item.create │
                                per-call watch list, 2s, only while live           ┘
```

## Open Questions

- Is `gpt-realtime-mini` a good enough presenter, or does brief delivery need the flagship? (Escape hatches ordered: flagship → Pipecat+Claude brain.)
- ~~Does direct SIP dialing to `sip.api.openai.com` work?~~ **Resolved 2026-09-01, the assignment ran:** yes over TLS from a real UA; the webhook event is `realtime.call.incoming` exactly as documented; a lowercased project id rings ~15s then 400s with no webhook. Webhook delivery verified via a plain-443 tunnel; **delivery to Funnel's `:8443` is answered below and the answer is no.**
- ~~Caller screening strength.~~ **Resolved by the gate in piece 3**, conditional on custom SIP headers reaching the webhook (probe 0). The earlier note that screening is "moot on the Twilio path" was wrong: the number routes anyone to the session.
- ~~Nudge injection mechanics.~~ **Resolved on paper 2026-09-02:** OpenAI's SIP guide documents `GET wss://api.openai.com/v1/realtime?call_id=…` after accept, "to stream events and issue realtime commands". The live attach-and-inject is probe 2 below and comes before any briefing code.
- ~~Does OpenAI deliver `realtime.call.incoming` to Funnel `:8443`?~~ **Resolved 2026-09-02, negative — probe 0a.** OpenAI's cloud never opens a connection to a Tailscale Funnel port other than 443. Three observations against one probe server, same token and same JSON-RPC, with only the ingress changed: `ts.net:8443` and `ts.net:10000` each answer 200 to a curl forced through the public ingress IPs (`185.40.234.55/.75/.198`), and each makes OpenAI return `424 Failed Dependency` in 0.78s with nothing arriving at the server, while a 443 tunnel completes the whole MCP handshake. A sub-second 424 is a refusal before any connect, not a timeout. A live INVITE with the dashboard endpoint still on `:8443` rang 15s and 400'd with an empty log; the endpoint row was read on screen (name “Incoming Call”, both `realtime.call.incoming` and `live.call.incoming` subscribed, signing secret present), so configuration was never at fault. **This retires D2.** Funnel's only non-443 ports are 8443 and 10000, so voice ingress now means Funnel on 443 (which today carries the tailnet-only relay), or a second `tailscaled` node with its own hostname funnelled on 443, or a named Cloudflare tunnel, or a public host.
- ~~Does `accept` take `tools: [{type:'mcp'}]`?~~ **Resolved 2026-09-02 — probe 1, both halves, without needing a call.** `POST /v1/realtime/client_secrets` takes the session verbatim with `tools:[{type:'mcp', server_label, server_url, headers, require_approval}]` and echoes it back with `headers.authorization` redacted, and the SIP guide says accept takes “the same parameters you would send in a create client secret request”. OpenAI also really fetches the URL: pointed at the probe over 443, `openai-mcp/1.0.0 (Responses API)` walked `server/discover`, `initialize`, `notifications/initialized`, `tools/list` and `tools/call` against this hand-rolled server and read `pong at …` back in its final message. No SSE, no `Mcp-Session-Id`, no approval step, 448 tokens. The literal `/accept` call stays unexercised and rides on probe 2.
- **Undocumented lead worth an admin key: `/v1/tunnels`.** The echoed session carries `connector_id` and **`tunnel_id`** beside `server_url`. Neither appears on the realtime-mcp page, and `GET /v1/tunnels` answers **403 “Please use an admin API key to access this endpoint”** rather than 404. If that is a first-party tunnel to a local MCP server it removes the MCP half of the ingress problem outright. Exploring it needs an `sk-admin-` key, so it is a question for the user rather than a probe.
- ~~Do custom SIP headers reach the webhook's `sip_headers`?~~ **Resolved 2026-09-02, yes — probe 0b.** `X-Relay-Call: probe-c3d29ca9` arrived verbatim, and `sip_headers` carries the **entire** request header set rather than the custom ones alone: `Via`, `Max-Forwards`, `From`, `To`, `Call-ID`, `CSeq`, `Contact`, `User-Agent`, `Allow`, the custom header, `Content-Type`, `Content-Length`. So the caller gate in T3 has the originating IP (`Via`/`From`/`Contact`) as well as a trunk marker, and the layered fallback named in the failure table is not needed. Confirmed twice, runs 2 and 3.
- ~~Can we attach `wss://…?call_id` and inject an item?~~ **Resolved 2026-09-02, yes — probe 2, live on a real call.** Auth: the **`headers` option** on Node's global (undici) WebSocket is honoured, `{headers:{authorization:'Bearer <key>'}}`, so OpenAI's browser subprotocol recipe is not needed and the key never rides in a URL. Two behaviours decide how the broker must be written:
  - **No `session.created` ever arrives.** The socket joins a session `accept` already made, so waiting for a session frame means never injecting. The ready signal is **`mcp_list_tools.completed`**, which lands ~2.5s after `accept` (measured 2.4s, 4.6s over four runs) — inject earlier and the model answers with no tools loaded and cannot call one.
  - **The first response always speaks the greeting in `instructions`**, whatever the injected item says. Three runs injected before it and all three spoke the greeting. So a nudge cannot ride the first turn; the broker injects after the first `response.done`.
  With both applied, the mechanic F7 depends on works end to end: second nudge at 11:11:14 → `response.created` → transcript *“Okay, let me do that now.”* → `response.mcp_call_arguments.done` → our server logs `tools/call` → `response.mcp_call.completed`, 3.9s from nudge to tool result. `usage` rides every `response.done`: 313–825 total tokens per response here, dominated by `reasoning_tokens` (69–553), with `cached_tokens` appearing from the second response on.
- **Two facts about the probe rig, not about OpenAI:** a call carrying no RTP gets a `BYE` from OpenAI at **~30s**, which bounds a medialess probe; and the socket then closes `1006`, which is teardown rather than an auth failure.
- ~~Delivery of `realtime.call.incoming` at all?~~ **Confirmed on 443 — probe 0a, positive half.** With the endpoint at `https://mbp5.taila6dcd6.ts.net/voice`, the webhook arrived 1.2s after the INVITE, signed, with `webhook-id: wh_6a9802e0…`. The Funnel mount is `--set-path=/voice`, and **Tailscale strips the mount prefix**, so the listener sees `/` (or `/webhook` for `…/voice/webhook`) and its own routes must be written for the stripped path.
- When Claude voice mode opens custom connectors, what carries over? (Everything except the broker and the listener, by design. Issue #190.)

## Success Criteria

- Acceptance demo (Codex's, adopted): call in, hear a roll-call that matches the DB, resolve one real agent question, hear the exact prompt read back, say yes, keep talking while it sends, verify one user row in the right chat, hear the next decision.
- A stranger dialing the number, or the SIP URI directly, never reaches a session that holds `voice_send`.
- Fixture tests assert every spoken field fits its speech budget, pin the ranking order (error / question status / prose question / unread / recency / dormant), and parse both question shapes; a local-only corpus test runs the same builder over the real `conductor.db` on this Mac.
- Cost: a logged real commute call lands within the estimated band; the README documents the measured number.
- Habit: used on real commutes five days in a row without reaching for the screen (except lock-screen artifacts).

## Eng review decisions (2026-09-02)

- **D1 — First PR: B, then everything in one PR.** Scope is all of approach B, on this branch, in one PR, built commit by commit in the order below, with a QA gate before deciding to merge. Chosen by the user over "milestone 1 only" and "all at once as one merge".
  - **Verified: nothing needs to merge to test this end to end.** The LaunchAgent runs the globally installed npm package, not a worktree, so a dev relay from this checkout (`RELAY_PORT=8788 RELAY_HOST=127.0.0.1 yarn start`, or `yarn dev`) runs the live source against the same read-only `conductor.db` and the same Conductor window. The voice listener takes its own loopback port, Funnel `:8443` is free today (`tailscale serve status` shows only `/ → 127.0.0.1:8787`, tailnet only), and the receipt pattern already exists for "another relay beside the installed LaunchAgent". The PWA parts of milestone 3 reach the phone from the dev relay over a tailnet-only `tailscale serve --https=<port>`. Three caveats, all from the code: `uiTurn` is process-local, so two relays are two locks and a phone send during a test call can interleave with a voice send; the two relays share `stateDir()`, and `parked-prompts.json` / `first-prompts.json` carry no multi-process guard, so a queued prompt could be delivered by both; and the notifier would push twice (the per-chat `tag` collapses it on the phone). The QA recipe therefore stops the installed relay for the session: `launchctl bootout gui/$(id -u)/no.adluna.conductor-remote` before, `yarn service restart` after.

- **D3 — Send shape: A, and the call assumes it lands.** `voice_send` answers `queued` at once; a landed send is silent; the broker speaks only for a parked or failed one.
- **D4 — Voice endpoint: A.** `/voice/mcp` with its own scoped token and only the voice tools. Discussed and recorded: this does not limit what an authenticated caller may ask for (the PIN gate does that); it limits what the credential can do at rest in OpenAI's store and what an injected model can do, since no direct send exists on that endpoint.
- **D5 — Deferred work is tracked as GitHub issues, never a TODOS file** (user convention). Opened: #189 (file the Linphone lowercasing bug upstream, with the repro) and #190 (recheck Claude voice for custom connectors on 2026-12-01).
